01 THE PROBLEM

A machine can be
booting but unreachable.

Presented by Sotir Usama Latif

When a remote Ubuntu system is still bringing up its network—or has no usable IP address or SSH service—there is no normal path in to see what is happening.

!

That is the blind spot. The system may be progressing, waiting, or failing, while the operator sees only a timeout.

This project explores an independent view of boot output through the EC2 Serial Console.

The guest can emit serial output before SSH is available.

02 WHY IT MATTERS

The hardest time to debug is often before the network is ready.

A remote login depends on several guest services being alive. A serial console gives a separate view into the boot process.

01
No usable route yet

No guest IPv4 address or route means the operator cannot address the machine through normal SSH.

02
The failure may be the network

If networking itself is broken, using that same path to diagnose it becomes circular.

03
Silence hides the boot state

A timeout cannot show whether Linux is waiting for a device, stuck at a prompt, or still booting.

✦ The target is an EC2 Ubuntu instance. EC2 uses virtual networking rather than Wi-Fi, but the same debugging gap appears whenever guest networking or SSH is not ready.

03 THE ACCESS PATH

A serial console is a side door to the guest.

It reaches the instance's serial port through AWS-managed access, instead of routing an SSH connection through the guest's IP network.

01
Separate from guest networking

The serial console is useful for boot and network troubleshooting even when the instance has no working network path.

02
Access is still controlled

Regional enablement and AWS IAM permissions are required; the console is not an unauthenticated endpoint.

03
AWS exposes the port abstraction

We work with the instance serial port and AWS console service; the lower-level fleet implementation stays AWS-managed.

09 PORTABLE BY DESIGN

Recreate the environment without baking in the instance.

Terraform outputs and runtime configuration let the same dashboard image point to a newly created instance.

STEP 01Clone the repo

Start with the source and infrastructure definitions.

git clone …
→
STEP 02Apply Terraform

Provision VPC, instance, IAM, and serial access in your account.

terraform apply
→
STEP 03Export target config

Instance ID, region, IP, and target flow into a local env file.

dashboard.env
→
STEP 04Run the image

Mount local credentials and SSH key; publish only on localhost.

docker run …
↻
Destroy → reapply → regenerate `dashboard.env`

The refreshed outputs let the dashboard follow the new instance ID and public IP.

Secrets stay outside the image

AWS profile + SSO cache and the EC2 key are mounted read-only. Terraform state stays in the local checkout.

Before applying in a new account: confirm region, AMI, key pair, IAM permissions, serial access, and restrict SSH ingress to a trusted address.
